# Fulmo の契約書面の作成

目的: 顧客の既存の契約と食い違わず、過去に締結した書面を踏襲し、Fulmo が自分の首を絞める約束を含まない書面を、手塚さんがそのままレビューできる状態で作る。良い書面は、目的の事項だけが書かれ、原契約の条番号と定義語にそろい、変わる値以外は過去の書面と同じ言い回しになっている。

このスキルの成果物は「担当者が作るドラフト」。社内の流れは、担当者がこのスキルで作成 → 手塚さんがレビュー（弁護士に回すかは手塚さんが判断する）→ OK が出たらクラウドサインで送付。

## 前提ルール: こちらから言及しない

Fulmo に不利な内容、明記・約束すると自分の首を絞める内容・条件には、こちらから言及しない。書面に書かないだけでなく、送付文や説明でも持ち出さない。相手方から求められている場合も草案には入れず、求められている条件・入れた場合の影響・応じ方の案を草案の外で示して、ユーザーの判断を待つ。具体的な判断基準は `references/defensive-rules.md`。

## 進め方

### 1. 既存の契約を確かめる（最初に必ず）

対象顧客について、次の原本を Drive（`references/templates.md` の「原本の探し方」）で集め、読む。
- 原契約: 利用申込書と、締結時点で適用されていた利用規約の版（申込書が参照するURL・版・締結日で特定する。同じURLでも中身が変わっている）、または業務委託契約書
- それまでに締結した覚書・合意書すべて（回数と日付）
- 顧客管理シートの契約情報（正式名称、代表者、住所、契約開始日、プラン）

原本から、当事者の正式名称・肩書き（合同会社は「代表社員」）・住所、原契約の名称と日付、契約期間、金額・料率、引用する条番号を取る。作る書面がこれらと食い違わないことを前提にする。原本がそろわないときは作成に入らず、見つからない書類と探した場所を示してユーザーに尋ねる。

### 2. 書面の種類を決め、テンプレートを選ぶ

`references/templates.md` の一覧から、目的に合う種類とテンプレートを選ぶ（例: 月額変更なら「変更覚書（月額変更）」、無償延長なら「契約期間に関する覚書」、満期解約でサイト譲渡なしなら「解約合意書_サイト譲渡なし」）。

### 3. 過去の類似事例を調べる

Drive と Slack（#法務_契約書、#営業_事務依頼、#cx_問い合わせ、#clc_only など）で、同じ種類・同じ事情の締結済みの書面を探す。
- 踏襲できる事例があれば、それをアレンジして作る。変えるのは今回の値と、事情の違いに必要な最小限の条項だけにする。
- 類似事例がない、または個別具体的な事情（紛争中、三者間、特例の条件、原契約にない新しい取り決め）がある場合は、テンプレートを土台にしつつ、各論点をユーザーに確認しながら進める。

### 4. ユーザーに確認する（2〜3問を1回にまとめる）

資料で確かめられる事実は自分で調べ、質問にしない。尋ねるのは次の3点で、それぞれ推奨の答えを付け、「はい」で推奨どおりに進められる形にする。

1. 選んだテンプレートと踏襲する過去事例（ファイル名とリンク）はこれでよいか
2. 今回変える値のうち、資料から確かめられなかったもの（効力発生日、金額、期間、対象サイトなど）
3. 相手方の要望や個別の事情（譲ってよい点・譲れない点、相手から求められている条件）

個別の事情があって論点が多い場合は、決まったことに応じて次の質問を続ける。

### 5. 書く

- テンプレートと踏襲元の docx をダウンロードし、書式（明朝10.5pt、条見出し「第X条（…）」、項は1から）を保ったまま値と必要な条項だけを変える。書式と定型の言い回しは `references/templates.md`。
- 原契約の条番号を名指しし、定義語は原契約にそろえる（原契約にない社内用語は使わない）。覚書が重なる顧客は「原契約（〇年〇月〇日付変更覚書による変更を含む）」「第N回変更覚書」のように日付と回数で特定し、「前回覚書」のような相対的な呼び方をしない。
- 締めに「本覚書に記載なき事項については原契約の規定が適用される」（長い覚書では優先条項も）を置く。
- 確かめられなかった値は推測で埋めず、【●】にして黄色の網掛けにする。
- 書き終えたら `references/defensive-rules.md` のチェックリストで読み直す。

### 6. 手塚さんへのレビュー依頼を用意する

次をそろえて渡す。Slack への投稿は、ユーザーが送ると言った場合だけ下書き（`slack_send_message_draft`）で用意する。
- 先方に渡す版の Word（社内メモなし）
- 社内確認メモ（別ファイルかチャット）: 書面の目的／原契約と過去の覚書（名称・日付・リンク）／使ったテンプレートと踏襲元／原契約・踏襲元からの変更点／こちらから言及しなかった論点とその理由／相手方に不利で交渉で指摘されそうな条項／【●】の箇所と確認先
- 手塚さん宛ての依頼文（短く。上のメモへのリンクと、特に見てほしい点を2〜3行）

### 7. クラウドサインの送付準備（手塚さんの OK が出たあと）

`references/cloudsign.md` の手順で行う。送信はしない（下書きまで）。
1. 最終版の Word を PDF に変換し、目視で崩れがないか確認する。
2. 宛先（会社名・氏名・メールアドレス）を顧客管理シートから取り、前回の締結時の宛先と照合する。食い違えばユーザーに確認する。
3. クラウドサイン API が使える環境なら `scripts/cloudsign_prepare.py` で下書き（書類・PDF・宛先）を作る。使えない環境なら、クラウドサインの画面にそのまま入力できる「入力シート」を出力する。

## 渡し方と保存

- 先方に渡す版は Word（.docx）。共有ドキュメントではなく最初から docx で作る。社内メモ・作成過程・確認用の注記は入れない。
- 保存先はユーザーが指定した Drive のフォルダ。指定がなければ作業フォルダに置き、場所を伝える。契約条件や取引先の情報を含むファイルはリポジトリにコミットしない。
- 締結後は社内 Drive に格納し、契約管理シートに期限などを転記するよう案内する。
