# CX 月次活動報告（調査 → 整理 → スライド）

2026年9月の全社会資料（FIX版）で確定した進め方と品質基準を再現するための手順。
**この順番で進める。順番を飛ばしてスライドを先に作らない。**

| 段階 | やること | 誰が |
|---|---|---|
| 1. 条件確認 | 対象月・報告の場・重点人物（例：CXマネージャー）を確定 | 自分 |
| 2. 調査 | Slack（重点人物の全投稿＋CXチャンネル）とDrive/Sheetsを並行調査 | `cx-report-researcher` ×2（Slack／Drive）を**同じメッセージで並列起動** |
| 3. 整理（チャット） | 全社会向け報告案をチャットで提示。取扱注意・要確認を分ける | 自分 |
| 4. 項目確定 | ユーザーが載せる項目と追加の一言を指定する（例：「⇒で次の打ち手」） | ユーザー |
| 5. 数値の裏取り | KPI（NRRなど）は算出元シートを直接読む | 自分 |
| 6. スライド生成 | `content.json` を書き、`scripts/build_deck.py` で生成 → Slidesアーティファクトへ publish | 自分 |
| 7. QA | `scripts/check_deck.py` → `cx-deck-reviewer` → 指摘を直して再publish | 自分＋サブエージェント |
| 8. 引き渡し | リンク・共有の注意（Shareしないと他人は開けない）・要確認点を伝える | 自分 |

## 1. 条件確認
- 対象月（例：2026年10月）、場（全社会／全社定例／Mgr会議）、重点人物（Slack表示名・ユーザーID）をはっきりさせる。
- 分からなければ、Slackで `slack_search_users` を使って重点人物のIDを引く。聞く必要があるのは「場」と「重点人物」だけ。

## 2. 調査（サブエージェント）
`references/research.md` の手順に沿う。2本の `cx-report-researcher` を**並列**で起動する（`subagent_type` がまだ一覧に無いセッションでは `general-purpose` に「`.claude/agents/cx-report-researcher.md` を読んでその指示に従え」と渡す）。
- A：Slack担当。重点人物の対象月の**全投稿**を時系列で最後のページまで読む。CX系チャンネル（`cx_` で始まる、`clc_only`、`cs_cx_` など）の主要スレッドも。
- B：Drive/Sheets担当。対象月に更新された Mgr会議資料・全社定例議事録・1on1議事録・CX定例・公式LINE分析・KPI算出シートなど。
- どちらも**読み取り専用**。認証情報・パスワード・個人の連絡先は報告に含めない。

## 3. 整理（チャットで提示）
報告案は次の形で出す（FIX時の承認済みフォーマット）：
1. 全社会向け報告案（テーマ別 3〜7項目。各項目は「何をした／結果／次」を1〜3行）
2. 重点人物の発信の要点（時系列の表）
3. 全社会に出すか判断が必要な情報（訴訟・資金繰り・返金額・個人評価・個人が特定される遅延指標など）
4. 確認していただきたい点（数値の食い違い、集計できなかった数値）

## 4. 項目確定
ユーザーが項目・言い回しを指定したら、それを**正**とする。自分が補った推測・提案は必ず【提案】と明記し、確定事項のように書かない。

## 5. 数値の裏取り
- KPIは算出元を直接読む（Slackで「NRR算出しました」等の投稿リンク → Sheets `get_values`）。
- 計算式を自分で検算し、定義（例：NRR＝(月初MRR−解約−ダウングレード＋アップグレード)÷月初MRR、新規は含めない）をスライドに書く。
- 月途中の値は、タイトルに「暫定」と書かず、※注記とスピーカーノートに書く。

## 6. スライド生成
1. 新規なら `Artifact` の `quickstart`（intent: slides）→ Slides 型で作成（`auto_open: "after_first_write"`）。既存デッキの更新ならその `url` を使う。
2. ロゴ `assets/fulmo_logo.png` を `asset: true` でアップロードし、返った `/_blob/<id>` を `content.json` の `logo` に入れる。人物写真などユーザー提供画像も同様。
3. `examples/content.example.json` をコピーして `content.json` を書く。スライド型は `references/design.md` の「スライド型」参照。**文章ルールは `references/writing.md`**。
4. 生成：`python3 scripts/build_deck.py content.json <root>` → `<root>/project/deck.json` と `<root>/project/slides/*.html`。
5. publish：`url`、`root=<root>`、`file_path=<root>/project/deck.json`、`files` に全スライド。消したスライドは `files` で `null`。
- デザイン値は `build_deck.py` 冒頭の定数でだけ管理する。スライドHTMLを手で直した場合は、同じ変更を content.json か定数にも反映して再生成できる状態を保つ。

## 7. QA
1. `python3 scripts/check_deck.py <root> content.json` — ERROR は必ず直す。WARN は内容を見て判断。
2. `cx-deck-reviewer` サブエージェントに `<root>` と `content.json` と調査結果（出典）を渡す。事実の裏付け・1枚1メッセージ・機密混入・読みやすさを見てもらい、指摘を直して再publish。
3. 見た目の最終確認は、ユーザーにアーティファクトで確認してもらう（この環境ではPPTXのレンダリングが不安定なため、はみ出しの可能性がある箇所を伝える）。

## 8. 引き渡し
- リンクを渡し、「まだ本人しか開けない。全社会前に Share から共有」「PPTX/PDFでダウンロード可」を伝える。
- 推測・提案・未確認の数値を箇条書きで明示する。

## FIX版から学んだこと（必ず守る）
`references/lessons.md` に全文。要点：
- **タイトル＝そのスライドの結論1文**（結果＋数値や状態）。抽象的な見出しは不可。
- 論点→根拠→示唆→意思決定は**思考の順番**。スライドにラベルとして出さない。読み手が流れを追える構成にする。
- 結論の先の打ち手は「**⇒ 〜**」の一文で明示する（例：⇒デポジット請求サイクルの即時化により解消を目指す）。
- KPIは可能なら**金額**で示す（「約半数」より「約◯◯万円〜◯◯万円」）。前提は※1、※2の注記で添える。
- 白背景・Fulmoパープル1色・濃い文字。本文34px（17pt）以上。グラデーションやグレーの面は使わない。
- 人事のお知らせは温かく（「新天地でのご活躍を…」）。写真はユーザー提供のものだけ使う。
